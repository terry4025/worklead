## 자동 지원 수리: CPU 과부하·지원 화면 미인식 (2026-11-08 09:24 KST 설치)

- **원인 A (CPU 70~90%·`request_timeout`)**: 리드 목록·상세가 목록 관찰 시각을 `(source_id, source_post_id) IN (VALUES …)`로 조회했다. SQLite가 `source_id` 접두어만 써서 당근 관찰 41.5만 행을 매번 훑었다(호출당 CPU 약 1.5초). UI가 `run.progress`마다 여러 큐를 다시 불러 백엔드가 포화됐다. 소스별 `source_post_id IN (…)`으로 바꿔 `ix_listing_source_post`를 타게 했다(`2ee15cd`). 운영 DB 복사본에서 큐별 목록·상세 1,516~1,922ms가 0~31ms로 줄었다.
- **원인 B (`ui_unrecognized`, 제출 0건)**: 당근이 공고의 첫 "지원하기"를 `<button>` 대신 `<a href=".../apply">`(role 없음)로 바꿨다. `auto-content.js`가 `button, a[role=button]`만 찾아 `openable`을 인식하지 못했고, 10초 대기 뒤 보류됐다. `/apply` 화면의 자기소개 패널 인식은 정상이었다. 링크도 동작 요소로 보도록 했다(라벨은 계속 완전 일치, `0c336ef`).
- **확인함**: 확장 109개(링크형 opener 테스트 추가), `test_auto_apply_browser.py`, 리드 관련 8개 파일 통과. 실제 공고(`svifvun8j45w`)에서 전용 Edge로 `openable → opened → ready`까지 확인했고, 최종 제출은 하지 않았다. 설치 후 2분 측정에서 백엔드 CPU는 한 코어의 1~7%였다. 5분마다 수집이 시작될 때 10초 정도 84%까지 오른다.
- **설치**: 백엔드 exe만 교체(데스크톱 앱은 변경 없음). 백업 `backups\pre-autoapply-fix-20261108\`. `quick_check ok`, 리드 2,625건, 자동 지원은 꺼짐 유지.
