# Worklead 리드 발견 지연·전국 범위·지원 동선 조사

조사일: 2026-10-16, 한국시간. 대상: `feat/daangn-cafe` 체크아웃과 현재 설치 DB. 사용자가 요청한 REA를 실제 사용했다. 제품 코드·설정·운영 DB를 변경하지 않았으며 실제 지원·채팅·게시를 실행하지 않았다. Computer Use와 컴퓨터 종료는 사용하지 않았다.

## 1. 결론

첨부 공고는 실제로 **20시간 55분 57초 늦게 발견**됐다. 단순히 화면의 ‘21시간 전’을 지연으로 읽은 결과가 아니라 원문 게시 시각과 DB 최초 발견 시각을 비교한 결과다.

현재 제품은 ‘전국 공개 목록에서 제작 의뢰를 주기적으로 선별하는 검토 도구’에 가깝다. ‘게시 직후 발견 → 즉시 알림 → 적합한 제안 → 지원 결과 추적’에 필요한 운영시간·발견 경로·알림 연결이 부족하다. 전국 주소를 많이 읽거나 한도를 모두 없애는 것만으로 해결되지 않는다.

이번 사례에서 **300회/일 또는 추가 후보 50회 제한이 지연의 직접 원인이라는 증거는 없다.** 전날 여러 탐색의 후보 목록에 이 글이 없었고, 이후 약 14시간의 탐색 공백이 있었다. 원본 목록의 시점별 기록이 없어 상류 노출 지연과 당시 제목·공개 상태 변경을 분리할 수 없다.

## 3. 첨부 사례의 지연을 어디까지 설명할 수 있나

저장된 실행 체크포인트의 후보 ID를 실제 `_ref_key` 해시로 대조했다.

14시간 공백 중 앱 종료·절전·일정 미실행 중 무엇이 발생했는지는 현재 DB만으로 구분하지 못한다. 코드상 수집은 앱 실행 중에만 동작한다.

## 5. 전국에서 ‘일할 만한 건’이 적어 보이는 이유

1. **발견 범위:** 사이트맵 공개 URL의 제목 단서로 선별한다. 모든 전국 게시판·본문·앱 전용 글을 보는 것이 아니다.
2. **유입 품질:** 저장된 당근 제외 사유에는 개발·자동화 아님 468회, 시급형 313회, 제작 의뢰 미확인 214회가 있다. 사유는 중복된다. 일반 채용을 많이 상세 조회하는 비용과 실제 적격 의뢰 수를 구분해야 한다.
3. **상품 범위:** 현재 품질 기준은 건당/프로젝트 개발 제작 의뢰다. 시간급·일급·월급, 운영 인력, 단순 디자인·교육 등은 제한된다. 전국 모든 ‘할 수 있는 일’을 포함하는 제품은 아니다.
4. **설정 표현의 부채:** 운영 프로필에는 `allow_short_term_employment=true`가 있지만 현재 `analysis/types.py:108`은 이를 레거시 필드로 두고 프로젝트 전용 적격성을 우선한다. 이 값만 바꿔 시간제 일을 늘릴 수 없다. 화면에 이 옵션이 노출된다면 실제 범위와 맞춰 정리해야 한다.
5. **미확인과 부적격 혼동:** 첨부 글은 구매 의도·건당 예산이 확인됐지만 원격 수행 여부만 미확인이다. 이런 글은 빠른 검토·질문 대상으로 올려야 한다. 반대로 확인된 저가를 적합도와 섞어 숨기거나 불명확한 보수를 낮은 보수로 간주하면 안 된다.

최근 상세 결과를 보존하는 표에는 당근 `collection_disallowed` 26개 ID와 `http_404` 18개 ID도 있다. 이는 전체 시장에서 빠진 의뢰 수가 아니라 마지막 조회 결과가 남은 ID 수다. 작성자의 수집 불허와 404를 ‘리드 0건’으로 숨기거나 일괄 제한 해제로 처리하지 않고, 발견 후보·조회 가능·적격·알림 전달 수를 별도로 보여줘야 한다.

먼저 현재 개발 서비스 안에서 누락과 우선순위를 고치고, 디자인·운영·시간제 계약까지 포함할지는 별도의 제품 범위로 결정해야 한다. 제외를 일괄 해제하면 구인 건수는 늘지만 맞는 의뢰 수와 채택 가능성이 함께 늘었다고 말할 수 없다.

## 6. REA로 당근 웹을 실제 분석한 결과

도구: [REA](https://github.com/morluto/rea)의 `capture_browser_scenario`, `analyze_javascript_application`, `export_evidence_bundle`. 설치된 공식 REA 스킬을 읽었다. 전용 임시 프로필의 headless Edge를 사용했고 로그인 정보·기존 사용자 프로필을 가져오지 않았다. 각 브라우저는 REA가 종료했다.

### 관찰한 것

- 공개 홈은 지역 기반 추천·검색이다. 검색창에 ‘상세페이지’를 입력하고 Enter를 눌러 실제 `/s?query=상세페이지&regionId=28`로 이동했다. 지역 선택 대화상자도 열었다. 관찰 범위에서 전국 단일 선택·검증된 최신순 전환은 확인하지 못했다.
- 검색 첫 화면에는 일반 채용과 무관해 보이는 결과도 섞였다. ‘검색어가 포함된 결과 제목만 반환된다’는 가정으로 수집을 구현하면 안 된다. 본문 매칭·추천 혼합·광고 여부는 이번 조사로 분리하지 못했다.
- 검색창 입력 시 제안 화면으로 전환되어 최초 ‘검색’ 버튼 클릭 시나리오는 시간초과했다. 같은 클릭을 반복하지 않고 Enter 동작으로 실제 검색 이동을 확인했다. 실패 기록도 보존했다.
- 홈 브라우저에는 245개 요청이 관찰됐다. 정적 자원·이미지·분석 서비스·인증 상태 확인이 포함된다. 이 수를 공고 245개 또는 수집 예산 245회와 동일시하지 않는다. 매 주기 새 브라우저로 홈을 전부 로드하는 방식은 가벼운 수집 방식이 아니다.
- 정상 웹 앱의 GraphQL 및 인증 상태 요청이 네트워크 메타데이터로 보였다. 요청/응답 본문과 헤더 값은 수집하지 않았고, 발견한 API를 별도 호출·재생하지 않았다. 이런 경로가 보인다고 공식 전국 실시간 API가 제공된 것은 아니다.
- 실제 첨부 원문을 공개 상태로 읽었다. 조사 시점은 **22시간 전, 건당 150,000원, 지원자 15명, 확인한 지원자 10명**이었다. 사용자 첨부 화면의 13명과 관찰 시점이 다르며, 증가 속도를 산출할 근거는 없다. 공개 브라우저의 ‘지원하기’와 첨부의 ‘지원 취소’는 세션이 다르다. 지원 상태를 바꾸지 않았다.
- 실제 DOM에서 관찰한 같은 호스트의 JS 청크 4개(총 48,356바이트)를 내려받아 SHA256을 기록하고 REA로 정적 분석했다. 4개 모두 파싱됐고 청크 일부에서 `endCursor`·`hasNextPage`를 확인했다. 정직원 피드 등 주변 코드가 포함된 제한 표본이다. **전체 검색 페이지네이션·전국 검색·서버 정렬의 실행 증거로 사용하지 않는다.** 정적 의미 관계에는 1,547개 미확정 항목이 남았다.

### 공개 사이트맵의 현재 상태

robots를 먼저 읽은 뒤 안내된 인덱스와 확인된 공고 sitemap 하나만 조회했다. 15:50 KST 표본에서 46,756개 URL, 약 12.1 MB였으며 `Cache-Control: public, max-age=300`이었다. ETag·Last-Modified는 제공되지 않았다. 첨부 글은 현재 포함되며 그 글의 `lastmod`는 게시 시각과 일치했다. 전체 목록의 최대 `lastmod`는 14:26 KST였다.

300초 캐시는 서버 내부의 목록 생성 주기가 5분이라는 보장이 아니다. 이 한 번의 조회로 게시→사이트맵 등재 지연이나 ‘모든 최신 글’을 측정할 수 없다. 소스 `lastmod`는 일반적으로 수정 시각이므로 게시 시각 대체값으로 쓰면 안 된다.

## 7. 개선 순서와 합격 기준

**1단계: 관측·알림·후보 우선순위.** 원본 최초 목록 노출 시각을 보존하고 첨부 제목 패턴을 우선 후보로 보완한다. 확인 필요 건 중 구매 제작 의뢰를 즉시 알리며 야간 누락을 복구한다. 최신 검토 목록을 제공한다. 기존 사용자 메모·초안·영업 상태를 보존한다.

**2단계: 신규 발견 전용 일정·큐·예산.** 새 ID를 먼저 상세 확인하고 오래된 갱신을 뒤로 보낸다. 앱 수집 heartbeat와 미실행 경고를 보이며 항상 실행 가능한 운영 환경을 별도 검증한다. 운영시간을 확보하지 않은 채 수분 단위 발견을 약속하면 안 된다.

현재처럼 인덱스+목록 최소 2회라면 전국 sitemap 감시는 5분마다 **576회/일**, 10분마다 **288회/일**, 15분마다 **192회/일**이다. 여기에는 상세·robots·재확인 요청이 빠져 있다. 300회 예산에서 5분 감시를 설정만 바꿔 달성할 수 없다. 15~30분 목록 감시를 초기 실험안으로 두고, 신규 상세 예산을 먼저 확보하며 실제 상류 지연을 측정한다. 조건부 요청도 HTTP 요청 수를 없애지는 않는다. 요청량을 조정하더라도 429·차단 대기와 인증 경계는 유지한다.

**3단계: 더 빠른 발견 경로의 검증.** 공개 지역 검색의 검색어·본문 일치·정렬·다음 페이지·누락을 먼저 검증한다. 전국 sitemap은 넓은 범위의 보완으로 유지한다. 전국 모든 지역×검색어를 무작정 순회하면 요청 수가 폭증한다. 전국 수분 단위 목표를 만족하려면 검증된 효율적 공개 경로 또는 공식 제공 피드/연동이 필요하며, 이번 REA 결과로 이를 확보했다고 말할 수 없다.

**4단계: 지원과 채택 동선.** 발견 즉시 요구사항과 사실 근거를 요약하고 해당 작업 포트폴리오, 가능한 일정, 범위 확인 질문을 준비한다. 지원 직전 모집 상태를 확인하고 원문 지원 결과를 기록한다. 이미 지원한 공고는 계정·원문 ID별로 중복 지원을 막는다. 빠른 응답 외에도 적합성·제안 품질·계약 조건이 채택에 영향을 주므로 지원자 수만으로 수주를 보장하지 않는다. 실제 지원 자동화는 이번 읽기 전용 조사에서 수행하지 않았다.

제안하는 지표는 `게시→첫 공개 목록 노출`, `첫 노출→발견`, `발견→알림`, `알림→지원`, `지원→응답→채택`이다. 1차 목표는 **지원되는 공개 경로에 노출된 뒤 발견 p95 15분 이내, 발견 후 알림 1분 이내**를 운영 실험으로 검증하는 것이다. 이 목표는 현재 달성 수치가 아니다. 최소 7일의 실제 운영·분리한 백필 집단·누락 평가 표본·차단/오류/운영 중단 기록이 있어야 ‘실사용 가능’으로 판정할 수 있다.
