# EXAONE 제거 · 기본 지원서 유지 · 수집 개선

작성 2026-11-19. 2026-11-10에 설치한 EXAONE 보조 기능(`docs/superpowers/specs/2026-11-09-exaone-ai-assist-design.md`)을 걷어 내고, 수집과 판정을 고친다.

## 1. 의도

- 사용자는 EXAONE을 앞으로 쓰지 않기로 했다. 이유는 네 가지다. 키를 넣을 수 없었고, 응답이 60~100초 걸리며, 약관상 상업 이용이 막혀 있고, 입력이 학습에 쓰인다.
- 처음에는 공고별 지원서를 자체 알고리즘으로 조합하려 했다(같은 파일의 첫 판, 커밋 9d14d96). 대화 끝에 사용자와 다음 판단에 합의했다.
  - 채택은 글보다 속도, 후기, 가격, 거리에 더 크게 갈린다.
  - 제목만으로는 요청을 알 수 없는 공고가 많다. 지금까지 나간 10건 중에도 "코딩 할 줄 아시는분", "블로그페이제작도와주실분"이 있다.
  - 반쯤 맞는 맞춤 글은 솔직한 일반 소개보다 기계처럼 보인다.
- 그래서 자동 지원은 당근에 저장된 기본 자기소개를 그대로 보낸다. 그 소개는 뉴던 원칙과 korean-humanizer 기준으로 한 번 다시 쓴다(앱 밖 작업, 5.6).
- 노력은 측정된 개선 여지가 있는 수집 쪽에 쓴다(11-10~11-19 실데이터).
  - 판정 규칙이 개발 의뢰 8~10건을 놓쳤다. 같은 기간 검토 대상은 32건이었다.
  - 원문 갱신 뒤 발견까지 중앙값이 32분이다. 앵커 재방문 간격의 중앙값은 35분이다.
  - 제목 필터가 3건을 놓쳤다.

## 2. 목표 · 비목표 · 반목표

**목표**
1. EXAONE의 코드, 설정, 화면, 데이터를 모두 걷어 낸다. OpenAI 분석은 EXAONE 이전 동작으로 남긴다.
2. 자동 지원을 EXAONE 이전 방식으로 되돌린다. 저장된 기본 소개를 확인하고(해시) 그대로 제출한다.
3. 의뢰 표현이 정형이 아니어서 제외되던 개발 의뢰를 규칙으로 잡아 '검토 필요'로 올린다.
4. 제목 필터가 놓치던 표현을 추가한다: 프로그래밍, html.
5. 개발 수요가 있는 앵커를 더 자주 보도록 빠른 확인 슬롯을 고친다(예산 안에서).
6. 기본 자기소개 초안 2~3개를 써서 사용자가 고르게 한다.

**비목표**
- 공고별 맞춤 지원서. 첫 줄만 맞추는 가벼운 맞춤도 지금은 하지 않는다. 2~3주 결과를 보고 다시 정한다.
- 채팅 답장 초안, 견적 초안. EXAONE과 함께 빠지며 대체 기능은 만들지 않는다.
- 아이보스와 당근 카페 수집 로직. 카페는 로그아웃 상태라 사용자가 다시 로그인해야 한다.
- 일일 요청 예산(5,500) 변경. 아래 속도 개선은 예산 안에서 한다.

**반목표** (동작은 하더라도 이렇게 되면 실패다)
- 규칙으로 "추정"한 공고에 자동 지원이 나가는 것. 추정 건은 사람이 본다.
- 기존 자동 지원 안전장치가 약해지는 것: 기본 소개 해시 대조, 1회 허가, 계정 확인, 일일 상한.
- 당근 요청량이 예산을 넘거나, 차단 중단 규칙(6초 간격, 429, 차단 감지)이 느슨해지는 것.

- 실제 사용자 DB(`%LOCALAPPDATA%\Worklead\worklead.sqlite3`)는 앱을 닫은 상태에서 설치 과정으로만 바꾼다. 데이터 정리는 마이그레이션이 맡는다.
- 당근 약관은 자동 수집에 사전 서면 동의를 요구한다. 이 설치의 수집 허용은 기존 사용자 확인에 근거한다(`docs/STATUS.md`). 요청량은 늘리더라도 조금만 늘린다.

## 4. 고려한 접근

| 접근 | 장점 | 단점 |
|---|---|---|
| A. 자체 지원서 조합기 | 공고마다 다른 글이 나간다. 무료이고 결정적이다. | 본문을 이해하지 못한다. 반쯤 맞는 맞춤의 위험이 있고 만드는 비용이 크다. 채택을 좌우하는 다른 요인은 그대로다. |
| **B. 기본 소개 유지 + 수집 개선 (선택)** | 측정된 구멍(판정 누락, 발견 지연)을 바로 메운다. 지원 글은 사람이 한 번 고르면 끝이라 위험이 없다. | 공고별 맞춤이 없다. |
| C. 기존 OpenAI로 맞춤 생성 | 문장 품질이 가장 높다. | 유료이고 공고를 외부로 보낸다. 대기와 실패 상태가 다시 생긴다. |

처음에는 A를 골랐다가, 대화 뒤 사용자가 B로 바꿨다(2026-11-19).

### 5.3 판정 규칙 보강 (추정 의뢰)

`analysis/rules.py`의 `classify_intent` 맨 끝, 판매자·구직·인력 채용 판정 다음에 둔다.
- 다음 세 가지가 모두 맞으면 `buyer_project`, 근거 `inferred`로 판정한다.
  1. 결과물 낱말과 만들기 낱말이 15자 안에 함께 있다.

  2. 사람에게 맡기는 표현이 있다: "분 구합니다/찾습니다/모집", "도와주실/도와주시면", "해 주실/해 주시면", "가능하신 분", "할 수 있는 분".

- `analysis/service.py`: 근거가 `inferred`인 구매 의뢰에는 검토 사유 "의뢰 표현 추정 — 원문 확인"을 붙인다. 그래서 최고 '검토 필요'까지만 올라간다. 시급·월급 표기 공고는 기존 `time_pay_review` 규칙(재택 개발 의뢰면 검토로)을 그대로 탄다.
- 11-10~11-19 실데이터의 기준 예
  - 잡혀야 한다: "AI 활용 웹사이트 제작"(10만원), "코딩할 수 있는 분 구합니다"(HTML/CSS 수정), "원격결재 시스템 구축", "상세페이지 제작 가능한분 구함", "웹디자이너) 재택 / 홈페이지 디자인 작업 가능하신분".

### 5.4 제목 필터

- 제목이 핵심 후보가 되려면 `title_pattern`과 함께 검색어 일치(`query_match`)도 필요하다. 검색어 일치는 사용자가 저장한 검색어와 `_TITLE_ALIASES` 동의어로 본다. 그래서 두 곳을 같이 고친다.
  - `sources/daangn/adapter.py`의 `_TITLE_ALIASES`: 프로그램 묶음에 `프로그래밍`을, 홈페이지 묶음에 `html`을 더한다.
  - `sources/daangn/profile.json`의 `title_pattern`에 `프로그래밍|html`을 더한다.
- 놓쳤던 예: "컴퓨터 프로그래밍 가능하신분 견적", "AI영상/ html 코드 제작가능하신분 찾습니다".
- `코드` 단독과 `봇` 표현은 넣지 않는다.
  - "코드"는 QR코드, 전선 코드 정돈 같은 비개발 제목에도 쓰인다.
  - "봇"은 사용자가 저장한 검색어 묶음에 없다. 검색어 범위를 넓히는 일은 사용자가 정한다.
  - 놓쳤던 예 "디스코드 노래봇 설정 알려주실분"은 교육성 요청이기도 하다.
- 기존 말뭉치 테스트(`test_daangn_m4_corpus.py`, `test_daangn_title_scope.py`)가 깨지지 않아야 한다. 강사 공고 제외(`_TEACHING_TITLE`)도 새 표현에 똑같이 적용한다.

### 5.5 발견 속도

**측정값** (11-12~11-19)
- 피드 작업 2.2만 건 중 95%가 "포화"로 기록됐다. 포화 기준이 `len(listed) >= 20`이라, 피드 한 페이지(20건)가 꽉 차기만 하면 포화가 된다. 그런데 방문당 새 항목은 평균 0.5~1.6건이다. 실제로 페이지를 넘쳐 놓칠 위험은 거의 없다.
- 빠른 확인 슬롯(10분당 8개)을 이 포화(최대 2개), 일시 오류 재시도(최대 2개), 수요 순위 앵커가 나눠 쓴다. 포화가 늘 참이라 2개 슬롯이 개발 수요가 아니라 게시량이 많은 앵커에 쓰인다.
- 개발 후보는 69개 앵커에 흩어져 있다. 상위 20개 앵커가 60%, 상위 30개가 75%를 차지한다.
- 당근 요청 사용량은 하루 2,900~4,100건이고 예산은 5,500건이다.

**변경**
1. 포화의 뜻을 실제 넘침 위험으로 고친다. `freshness.py`의 포화 선정이 `feed_saturated` 대신 `new_listed_entries >= 15`(페이지의 3/4)를 본다. `adapter.py`의 `feed_saturated`는 "페이지가 꽉 찼다"는 기록으로 그대로 둔다. `executors.py`는 남의 미커밋 변경이 있으므로 건드리지 않는다.
2. 수요가 없는 앵커의 확인 간격을 늘리고, 아낀 요청을 빠른 확인에 돌린다.
   - 지난 30일 동안 개발 후보를 하나도 내지 않은 A 등급 앵커 9개를 C 등급(120분)으로 내린다. 대상 지역 ID: 672, 837, 2236, 2565, 3630, 4602, 5227, 6452, 6652.
   - `adaptive.max_hot_anchors`를 8에서 10으로 올린다.
   - 이유: 수집기는 빠른 확인 슬롯 수 × 하루 확인 횟수만큼 목록 요청을 미리 떼어 둔다(`remaining_list_requests`). 16개로 올리면 이 몫이 예산 5,500을 넘어 상세 확인 요청이 남지 않는다.
   - 조건: 하루 목록 예약량 `daily_list_requests(5)`가 지금 값 4,864 이하여야 한다. 9개를 내리고(−324) 2슬롯을 늘리면(+288) 4,828이 된다.

**목표와 한계**
- 포화 오판을 고치면 빠른 슬롯 대부분이 수요 순위 앵커로 간다. 슬롯 증가와 합쳐서, 수요 앵커에 쓰는 빠른 슬롯이 약 6개에서 10개로 는다.
