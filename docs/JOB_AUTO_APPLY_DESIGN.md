# 저장된 자기소개를 사용하는 점수 기준 자동 지원안 (2026-10-24)

> 2026-10-25 후속 사용자 지시로 **50점 이상 자동 지원 구현**으로 범위를 변경했다. 아래는 최초 설계 이력이다. 현재 사용 방법과 구현/실사이트 검증 범위는 [자동 지원 안내](JOB_AUTO_APPLY.md)와 [STATUS](STATUS.md)를 따른다. 기존 초안 API는 유지하며 실제 제출은 별도의 자동 지원 기능에서만 실행한다.

사용자 요청은 탐색 결과 자동 반영의 구현과 자동 지원 **방법 설명**이다. 이번 변경은 실제 지원 전송을 활성화하지 않는다. 현재 `applications.py`의 `draft_only`/제출 거부와 메시지 전용 확장의 읽기 범위를 유지한다.

## 관찰한 화면

제공된 스크린샷은 공고의 ‘지원하기’ → ‘제출할 자기소개를 확인하세요’ 패널 → 패널의 ‘지원하기’ 흐름이다. 사용자가 이미 저장한 소개를 그대로 쓰면 자동 입력이 필요 없는 경우가 있다. 두 번째 클릭은 실제 외부 제출이다.

첨부 HTML을 읽기 전용으로 분석한 결과 자기소개 패널의 DOM은 없었다. `form=0`, `textarea=0`, `contenteditable=0`, `dialog=0`이며 자기소개·미리보기·약관/동의·지원 완료·이미 지원 상태를 확인하지 못했다. 그러므로 최종 버튼의 정확한 선택자, 추가 질문 없음, 제출 성공 판정까지 검증한 자료는 아니다. 다른 공고도 항상 두 번 클릭이라고 일반화하지 않는다. 원본 HTML/소개/계정명/추적값은 저장소나 진단 자료로 복제하지 않는다.

## 구현할 흐름

1. 수집·분석 커밋 뒤, 사용자가 설정한 점수 이상인 당근 제작 의뢰를 지원 대기열에 넣는다. 예를 들어 85점은 **후보 진입 기준의 예시**이며 채택 확률이나 수익성 보장이 아니다. 수집 이벤트·화면 재접속·과거 이벤트 재생이 중복 제출을 만들지 않도록 공고별 영속 중복 키를 사용한다. 켜기 전 과거 공고를 기본적으로 소급 제출하지 않는다.
2. 제출 직전에 해당 공고를 정상 웹 화면에서 다시 확인한다. 공고 ID·제목·모집 상태·현재 점수/조건을 대조하고, 지원 취소 표시 또는 지원 내역이 있으면 `already_applied`로 건너뛴다. 이 확인이 실패하면 제출하지 않는다. 다른 글로 이동한 탭에서 버튼 이름만 찾아 누르지 않는다.
3. 첫 ‘지원하기’를 누르고 해당 공고의 자기소개 패널을 기다린다. 승인해 둔 소개 버전과 현재 선택 내용을 대조한다. 소개 내용이 바뀌었거나 필수 질문·새 동의·본인인증·앱 전용 화면 등이 나타나면 `held`로 보류한다. 답을 추측하거나 다른 자기소개로 바꾸지 않는다.
4. 최종 클릭 전에 공고별 시도 잠금·일일 제출 한도와 `submitting` 상태를 DB에 먼저 기록한다. 승인한 소개를 사용하는 정상 확인 패널에서 최종 ‘지원하기’를 **한 번만** 누른다. 같은 공고의 동시 작업과 앱 재시작이 두 번째 제출을 만들지 못하게 한다.
5. 해당 공고의 공식 완료 표시/지원 내역으로만 `submitted`를 확정한다. 타임아웃·브라우저 종료·응답 유실은 `uncertain`으로 남겨 자동 재클릭을 막는다. 이후 지원 내역 대조로만 해소한다. 네트워크 200이나 버튼 클릭 실행 자체를 성공으로 세지 않는다.

상태: `eligible → opening → reviewing_profile → submitting → submitted`, 분기 `held / already_applied / uncertain / failed_before_submit`. `submitting`에서 프로세스가 끊겨도 자동 재제출하지 않는다.

## 한 번 설정할 항목

- 자동 지원 기본 꺼짐, 실행을 켜는 시점, 중지 버튼.
- 최소 점수(0~100), 포함할 추천/확인 필요 분류, 모집 중·제작 의뢰 범위, 보수/재택/대면/추가 질문의 허용 조건.
- 저장된 당근 자기소개 중 제출할 버전. Worklead 프로필이 아니라 **실제 당근 화면에서 선택된 소개**를 확인한다. 기존 ‘프로필은 초안에만’ 선택은 자동으로 제출 동의로 바꾸지 않는다.
- 하루 제출 상한과 첫 검증 대상 공고. 조건 승인 후에는 공고마다 별도 수동 확인 없이 실행하는 구조로 만들 수 있다. 조건 밖·불확실한 공고만 보류한다.

첨부 예시는 제작 의뢰와 건당 보수가 보이지만 재택·대면 조건이 명시됐다는 근거는 부족하다. 점수가 높더라도 설정한 보류 조건을 별도로 검사해야 한다. 사업자 계약/세금계산서 필수처럼 저장된 소개와 충돌하는 요구도 보류 조건이다.

## 현재 구현과 필요한 확장

- 백엔드: 제출 정책·영속 시도 기록·잠금·재시작 복구·완료 대조·감사 로그가 필요하다. 현재 `/submit`은 `409 application_submission_unavailable`, `sent=0`을 반환한다.
- 브라우저: 실제 로그인한 크롬에서 정상 화면의 단계별 버튼을 조작할 실행부가 필요하다. 지금 확장은 미읽음 상태만 전달하며 지원 클릭 명령을 받지 않는다. 메시지 연결 키에 제출 권한을 섞거나 쿠키/비공개 API를 추출하는 방식으로 확장하지 않는다.
- 화면: 점수·소개·한도·보류 조건과 마지막 제출 결과를 한곳에서 표시한다. ‘버튼 누름’, ‘제출 확인’, ‘채택/수금’을 별도로 집계한다.
- 검증: 가짜 사이트에서 2단계 흐름·추가 질문·잘못된 공고·소개 변경·이미 지원·동시 작업·응답 유실·재시작을 검사한 다음, 사용자가 지정하고 제출을 승인한 실제 공고 한 건의 공식 완료 상태를 확인한다.

## 이번에 구현한 자동 반영

수집 진행·리드 생성/변경·분석 완료·실행 완료 이벤트를 250ms 단위로 모아 활성 목록을 다시 조회한다. 읽던 상세·메모·초안은 유지한다. 연결 복구 시 다시 조회하고, 연결이 끊긴 동안 30초마다 로컬 데이터 조회로 보완한다. 실행 상태 폴링에서 새 완료가 발견돼도 반영한다. 실패한 목록은 이전 데이터를 유지하고 30초 뒤 다시 시도한다. 이것은 **수집된 결과의 화면 반영**이며 외부 수집 주기나 사이트에 새 글이 올라온 순간의 발견 시간을 250ms로 보장하는 기능이 아니다.

비활성 필터의 캐시도 오래된 것으로 표시해 다시 열 때 재조회한다. 구현은 설치된 TanStack Query의 `invalidateQueries`/`refetchQueries`를 사용한다. [공식 캐시 무효화 문서](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation).
