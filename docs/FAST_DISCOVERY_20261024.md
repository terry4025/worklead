# 당근알바 빠른 탐색 조정 (2026-10-25)

## 확인한 병목

설치 DB를 읽기 전용으로 조사했다. 기존 설정은 탐색 15분이지만, 최근 실행은 HTTP 70~98회로 약 7~10분이 걸린 다음 15~16분을 더 기다렸다. 같은 A 앵커의 실제 재방문은 약 22~26분이었다. 결과는 개별 상세 처리 후 저장되므로 전체 탐색 완료까지 기다리는 구조는 아니었다.

공개 목록은 99개 앵커 동네의 첫 20건이고, 제목·직종 필터를 통과한 후보만 상세를 확인한다. 모든 지역·공고를 포괄하거나 누구보다 먼저 발견한다고 보장할 수 없다. 최근 하루 30개 앵커에서 제작 후보가 보였지만, 반복해서 보이는 같은 글을 생산성으로 합산하면 우선순위가 왜곡된다.

## 변경

- 기본 탐색 주기를 5분으로 줄인다. 매번 전국 99개를 재조회하는 대신, 확인 시각이 된 앵커만 조회한다.
- 일반 A 앵커는 최소 30분, C 앵커는 최소 120분을 유지한다. 최근 30일 신규 제작 후보를 처음 관찰한 앵커 중 최대 8개는 10분 우선 확인한다. 최초 설치 기록에 신규 관찰 수가 없으면 최근 후보 관찰 기록으로 한정해 시작한다.
- 인접 지역에서 같은 공고를 봐도 최초 관찰은 전역에서 한 번만 센다. 기존 후보의 재등장 횟수는 생산성에 더하지 않는다.
- 순위가 수시로 바뀌어도 요청이 늘어나지 않도록, 모든 우선 앵커가 최근 10분 동안 완료된 우선 조회 8회 한도를 공유한다.
- 기존 5분 시각 여유를 우선 감시에 적용하지 않는다. 10분 주기가 실제로 5분마다 조회되는 문제를 막는다. 우선 앵커를 일반 앵커보다 먼저 처리한다.
- HTTP 최소 6초 간격, robots, 429의 Retry-After, 401/403·차단 화면 정지, 호스트의 하루 5,500회 한도를 유지한다. 작업이 중첩되거나 앱이 꺼진 기간의 실행이 한꺼번에 쌓이지 않는다.

목록 조회는 고정 hot 앵커만 가정한 4,480회 대신, 순위가 회전하는 경우까지 보수적으로 하루 4,864회를 예약한다. 최초 동기화 여유 109회를 더하면 4,973회다. 이는 응답 지연을 빼서 추정한 속도 수치가 아니다. 실제 요청·재시도·robots 조회는 같은 5,500회 한도를 공유하고, 남은 목록 감시 예산이 부족하면 선택 상세 조회를 유예한다. 전체 시장을 짧은 초 단위로 전수 재조회하지 않는다.

후속 전국 누락 감사에서 정상 완료한 당근 탐색은 **직전 시작 시각+5분**을 다음 점검 기준으로 바꿨다. 실패/부분 완료/취소와 다른 소스는 기존 종료 기준 대기를 유지한다. 진행 중 중복 예약과 밀린 실행 재생은 하지 않는다. 첫 동기화, 서버 지연, 상세 후보 증가, 다른 수집 작업, 재시도 때문에 실제 지역별 재방문은 10·30·120분보다 길 수 있다. [현재 실측·누락 보완](NATIONWIDE_OPPORTUNITY_AUDIT_20261025.md)을 따른다.

## 자동 지원과의 관계

이 변경은 공개 탐색과 후보 저장을 빠르게 한다. 점수 50점 이상을 제출 대상으로 삼는 자동 지원의 동의·저장 소개 대조·중복 방지·불확실한 제출 결과의 재시도 차단은 별도 기능이다. 이 탐색 검증에서는 실제 지원·메시지 발송을 하지 않았다.

## 검증

합성 공개 HTML, SQLite, 실제 워커를 사용한 회귀 검사로 신규 관찰 앵커의 10분 우선 확인, 일반 앵커의 30분 유지, 5분 중복 조회 방지, 겹치는 지역의 최초 관찰 1회, 반복 후보의 생산성 제외, 30일 경과 기록 제외, 우선 조회 공유 한도, 하루 예산 예약 상한을 확인한다. 실사이트에서 달라진 지연과 장시간 운전의 요청량은 별도 관찰이 필요하다.
