# M3: 기존 공고 처리 진단과 제출 전 일시 실패 복구

## 범위

사용자가 시작한 자동 지원 연결이 정상일 때 새 공고와 기존 저장 미지원 공고를 같은 조건으로 검토한다. 50점·하루 기본 20건·기존 수집 허가/예산/간격·공개 원문 재확인·저장 기본 소개·추가 질문 보류를 유지한다. 실제 Chrome 연결, 실제 제출 완료, 답장 알림의 운영 관문은 별도로 판정한다.

## 제한 재시도

다음 조건을 모두 만족해야 자동으로 다시 검토한다.

- 제출 허가 시각 `permitted_at`이 없고, DB 밖 제출 journal에 같은 공개 공고 키도 없다. journal 손상/읽기 실패는 진행을 차단한다.
- 상태가 제출 중·결과 미확인·제출 완료·기지원이 아니다.
- 원인이 공고 이동 실패, 브라우저 동작 시간초과, 제출 전 연결 종료 또는 처리 임대 만료로 확인됐다.
- 재시도 상한에 도달하지 않았고 예정 시각이 됐다.
- 현재 점수·작업 조건·사용자 표시·모집 상태·수집 허가·당일 상한을 다시 통과한다.

초기 처리 이후 **1분·5분·15분 간격으로 최대 3회** 재검토한다. 같은 공개 공고의 DB 행을 재사용해 고유성을 유지하고, 이전 처리/완료 대조 키를 폐기한 뒤 새 처리 키를 발급한다. 재시작해도 예약 시각과 사용 횟수를 보존한다.

양식 미인식, 추가 질문/동의, 소개/계정 변경, 수동 중지, 조건 충돌은 자동 재시도하지 않는다. **제출 허가 준비 이후의 오류를 제출 전 오류로 낮춰 재처리하지 않는다.** 허가 응답 소실이나 불확실한 결과에는 기존 읽기 전용 완료 대조만 수행한다.

0008의 기존 보류도 알려진 일시 실패·재시도 0회·허가 시각 없음·journal 없음인 행만 최초 1분 대기에 편입한다. 기존 질문·양식 미인식·수동 취소·불확실한 제출을 일괄 해제하지 않는다. 이미 예약한 시각을 재시작 때 늘리지 않는다.

## 기존 공고와 원문 재확인

게시 후 24시간이 지난 글의 일시 실패 보고에 현재 양식 증거가 없다는 이유만으로 영구 보류하지 않는다. 실제 제출 허가에는 **현재 공개 원문의 유효한 확인과 현재 저장 소개 양식**이 모두 필요하다.

원문 TTL이 지나면 기존 `recheck_stale`을 예약한다. 분당 최대 한 개 예약, 같은 작업 중복 방지, 기존 backoff/상세 수집 허가를 유지한다. 진단 화면 조회는 수집 예약·외부 요청을 하지 않는다. 작업의 대기·진행·중지·실패·부분 완료와 마지막 원문 확인 시각을 구분하고, 작업 성공을 지원 조건 통과로 단정하지 않는다.

## 화면

공고별 대기·제외·원문 재확인·양식 확인·제출 허가·완료·기지원·재시도 대기·영구 보류·결과 미확인을 표시한다. 재시도 횟수/예정 시각과 사유에서 원래 리드로 이동할 수 있다. 불확실한 결과를 덮어쓰는 재지원 버튼은 추가하지 않는다.

`queue_reason`은 중지·계정/소개 확인·최초 연결 대기·연결 미응답·당일 상한·기존 처리·수집 허가·원문 확인·재시도 대기·후보 없음·다음 후보 준비를 구분한다. 최초 작업 요청도 90초 이상 없으면 `needs_user_action` 화면 경고를 표시하며 이전 `connected` 응답을 정상 실행으로 계속 표시하지 않는다.

매 2초 조회에서 전국 저장 데이터를 전부 분석하지 않는다. 최근 고점수 후보 최대 100건과 최근 처리 기록을 살펴 최대 30건을 표시하고, 진단은 최대 15초 캐시한다. 이 목록은 전국 전체 구인 수나 모든 저장 공고의 전수 진단이 아니다. 전국 누락·발견 지연 측정은 M4에 남아 있다.

## 호환·적용

DB `0009_auto_apply_retry`는 `retry_count`·`retry_after`를 추가한다. 공고 유일 키·제출 허가·journal을 유지하며 0008 백업도 분리 검증·마이그레이션한다. 업데이트 전에 기존 DB·실행 파일·journal을 보존한다.

확장 0.6.0은 제출 전 일시 실패를 구분하고, 허가 준비 이후에는 재검토 요청을 보내지 않는다. M2의 메시지/자동 지원 허가·저장 계정과 호환된다. 준비 폴더 갱신과 Chrome의 실행 확장 새로고침은 별도다.
