## 확인한 누락 경로

1. **처리 대기 중 유실**: 상세 한도 때문에 미룬 후보는 DB에 목록 정보가 있어도 다음 공개 첫 페이지에 다시 보여야 처리됐다. 페이지에서 밀려난 글은 사이트맵/다음 노출까지 기다릴 수 있었다. 당시 선택 목록은 핵심 403개·추가 213개였으며, 상세 시도 기록은 각각 401개·207개였다. 모든 차이를 버그로 세면 안 된다. `collection_disallowed`, 숨김, 오류와 backoff를 구분해야 한다.
2. **구매 의도 오분류**: ‘홈페이지 리뉴얼을 도와주실’, ‘웹&앱 구현도 해주실’, ‘웹사이트를 앱으로 등록하는 작업’, ‘웹사이트 디자인작업등을 도와주실’ 등의 명시 납품 표현을 놓쳤다. 1,172건을 동일 시각·프로필·피드백으로 이전/수정 규칙에 재생하면 확인 필요 14→18, 제외 1,158→1,154였다. 복구된 4건은 저장 당시 원문 기준이며 오래된 글도 포함한다. 신규 모집·실제 수행 가능·수주를 확인한 4건이라는 의미는 아니다. 시간 보수와 마감은 계속 제외했다.
3. **실제 범위 공백**: 앵커 반경 밖, 다른 직종, 첫 20건 밖, 제목에 기술 표현이 없는 글은 빠질 수 있다. 저장 목록의 filtered 약 19만 건은 제목 단계에서 제외된 주소이며, 이 수를 ‘놓친 제작 의뢰 수’라고 주장할 근거는 없다. 전국 대상 수집과 전국 모든 구인글 확보는 다르다.
4. **수집 불허와 누락의 혼동**: 공개 검색에서 보인 ‘웹사이트 개발자를 구합니다.’는 이미 core로 발견됐지만 상세 시도가 `collection_disallowed`였다. 우회하거나 정상 공고 수로 부풀리지 않는다. 사용자가 화면에서 볼 수 있다는 사실만으로 수집기가 본문을 저장할 수 있다고 판단하지 않는다.

## 이번 수정

- 어댑터 0.8.1은 최근 7일에 공개 목록에서 선별했지만 **아직 한 번도 상세를 시도하지 않은** 후보를 영속 목록에서 이어받는다. 현재 활성 검색어로 다시 선별하고 최신 후보를 먼저, 실행당 최대 40개만 검토한다. 새로운 목록 요청은 필요 없다. 실패/불허/기존 기록은 본래 backoff·재확인 경로에 남긴다. 약한 후보를 핵심 후보로 승격하지 않는다.
- 이어받기는 현재 공개 피드 작업 뒤에 실행하며 같은 상세 한도·일일 예산·6초 간격·목록 예산 예약을 공유한다. 최초 목록 관찰 시각을 갱신하지 않는다. 화면 실행 기록에 ‘저장 목록에서 이어받은 미처리 후보’를 표시한다. 재시도 시간이나 수집 허용 상태를 바꾸는 기능이 아니다.
- 규칙 `rules-2026.10.25-delivery`는 구체적인 디지털 납품 대상·변경 작업·도움 요청이 함께 있는 표현을 구매 수요로 인식한다. 포트폴리오 조언, 교육, 판매자 홍보, 일반 회원가입/앱 설치, 직원 채용과 물리 작업은 제외한다. 점수 가중치와 50점 기준은 바꾸지 않았다. 불명확한 원격 조건은 확인 필요로 유지한다.
- 정상 완료한 당근 탐색은 시작 시각+5분으로 다음 점검을 계산해 실행 시간만큼 대기를 누적하지 않는다. 진행 중에는 중복 예약하지 않고, 실패/부분 완료/취소는 기존 종료 후 대기, host cooldown·429는 그대로다. 절전 중 밀린 실행을 연속 재생하지 않는다. 다른 소스 주기·재확인 주기는 바꾸지 않는다.
- 원문에서 확인한 건당 제작 구매 수요를 우선 지역 선정에 사용한다. 단순한 ‘활동 프로그램’ 제목의 빈도가 실제 제작 의뢰 지역을 밀어내지 않게 했다. 한 리드는 최초 피드 하나에만 성과를 부여한다. 분석 이력이 아직 없을 때는 기존 제목 후보를 초기 기준으로 사용한다. 최대 8개/10분의 공유 우선 조회 한도는 유지한다.
