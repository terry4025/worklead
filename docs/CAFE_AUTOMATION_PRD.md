## 1. 배경

사용자는 컴공 출신 2년차 프리랜서 개발자다. Worklead는 원격으로 할 수 있는 개발 외주 의뢰를 찾아 검토하는 Windows 데스크톱 앱이다(Tauri 2 + React 화면 + Python FastAPI sidecar + SQLite). 지금은 당근알바(`jobs.daangn.com`) 공개 사이트맵과 i-boss를 로그인 없이 수집한다.

사용자는 **당근 카페**(웹 `www.daangn.com`의 카페 기능. 예: "단기알바는요기" 카페의 "아르바이트구인구직" 게시판)에 웹·소프트웨어 개발 의뢰가 자주 올라온다는 것을 확인했다. 같은 카페들에 자기 구직글을 올리고, 그 글에 달린 문의를 놓치지 않으려 한다.

기존 문서는 다음을 범위 밖으로 두었다.

사용자가 2026-10-12에 다음을 요청했다: 당근 카페의 개발 의뢰 글을 Worklead가 찾아오게 하고, 글을 올릴 만한 카페에 정해진 구직글을 자동으로 쓰고(이미 쓴 카페는 건너뜀), 그 글에 달린 댓글 요청을 Worklead에서 보게 해 달라.

이에 따라 범위를 다음처럼 **좁게** 바꾼다. 위 세 문서에 이 변경을 날짜와 함께 기록한다.

| 바뀌는 것 | 그대로인 것 |
| --- | --- |
| 사용자가 **직접 로그인한** 전용 브라우저 프로필로 당근 카페를 읽는다 | 비밀번호를 앱이 입력·저장하지 않는다 |
| 승인된 카페에 **사용자의 구직글 1건**을 게시한다 | 자동 댓글·자동 답글·자동 채팅 발송은 하지 않는다 |
| 내 글의 댓글을 읽어 문의함에 보여준다 | 자동 지원, 계약 확정, 결제는 하지 않는다 |
| | CAPTCHA·본인 인증·차단 회피는 하지 않는다 (§7) |

당근 이용약관은 자동화 도구 사용에 사전 서면 동의를 요구한다(`docs/SOURCE_RESEARCH.md:51`). 반복 홍보글은 계정 제재 사유가 될 수 있다. 앱의 카페 기능 첫 화면에 이 위험을 한 문단으로 보여주고, 사용자가 "확인" 해야 기능이 켜지게 한다. 확인 기록(시각·문구 버전)을 DB에 남긴다.

## 3. 기능 요구사항

### F0. 카페 세션 (공통 기반)

- 시스템 Microsoft Edge를 쓰는 Playwright 영속 프로필(`channel="msedge"`, `launch_persistent_context`)을 사용한다. 프로필 경로는 `%LOCALAPPDATA%\Worklead\cafe-browser\`. 사용자가 브라우저를 따로 설치하지 않게 한다.
  - Playwright가 PyInstaller sidecar에 들어가지 않거나 크기·안정성 문제가 크면, 대안(Tauri 쪽 WebView2 창 등)을 비교한 결과를 `docs/CAFE_RESEARCH.md`에 적고 더 단순한 쪽을 고른다.
- 사용자 결정(2026-10-12): Chrome 기본 프로필은 쓰지 않는다(Chrome 136부터 기본 프로필의 원격 조종이 막혀 있음). **Edge 전용 프로필 하나로 고정**한다.
- 카페 작업을 시작할 때마다 먼저 로그인 상태를 확인한다. 이미 로그인되어 있으면 로그인 단계 없이 바로 진행한다. 로그인이 안 되어 있을 때만 "브라우저 열어 로그인" 버튼을 보여준다. 이 버튼은 보이는 Edge 창으로 당근 웹을 열고, 사용자가 직접 로그인한다. 앱은 로그인 완료 여부만 확인한다(예: 프로필/내 정보 영역 존재). 로그인은 프로필에 남으므로 보통 처음 한 번만 하면 된다.
- 세션 상태를 `logged_out / logged_in / needs_user`(인증·CAPTCHA·약관 동의 화면 등)로 저장하고 화면 상단 IssueStrip에 표시한다. `needs_user`가 되면 카페 작업 전체를 멈추고 Windows 알림 1회를 보낸다(기존 `native_notifications` 사용).
- 모든 카페 페이지 이동은 하나의 큐로 직렬 처리한다. 기본 한도: 페이지 이동 최소 간격 8초, 하루 300회. 설정에서 바꿀 수 있다. 무작위 지연이나 사람 흉내를 넣지 않는다. 고정 간격만 쓴다.
- 앱이 실행 중일 때만 동작한다(기존 자동 수집과 같다).
- 헤드리스로 정상 동작하면 헤드리스, 아니면 최소화된 보이는 창을 쓴다. User-Agent·지문 위조는 하지 않는다.

### F1. 카페 찾기와 분류

- 카페 검색·카테고리(예: 직업/커리어)·지역 화면에서 후보 카페를 찾는다. 기본 검색어: `알바`, `구인구직`, `아르바이트`, `외주`, `프리랜서`, `개발`, `IT`, `부업`, `재택`. 설정에서 수정할 수 있다.
- 사용자가 카페 URL을 직접 추가할 수도 있다.
- 각 카페에 대해 저장할 것: 이름, URL, 지역, 카테고리, 멤버 수, 게시글 수, 가입 여부, 게시판 목록, 공지 요약(홍보 규칙 판단 근거 문장).
- 카페 상태:

| 상태 | 뜻 |
| --- | --- |
| `candidate` | 찾았지만 아직 판정 전 |
| `needs_join` | 글을 쓰려면 가입이 필요. **가입은 사용자가 직접 한다.** 앱은 "카페 열기" 버튼만 준다 |
| `eligible` | 가입됨 + 구직·홍보가 허용되는 게시판이 있음 |
| `approved` | 사용자가 게시 대상으로 승인함 |
| `excluded` | 규칙상 홍보 금지, 관련 없음, 사용자가 제외 |

- 게시판 판정 규칙: 게시판 이름에 `구직`, `구인구직`, `알바 구인`, `홍보`, `재능`, `프리랜서`, `외주` 등이 있으면 후보로 본다. 공지·게시판 설명에 `홍보 금지`, `광고 금지`, `외부 링크 금지`, `구직글 금지` 등이 있으면 `excluded`로 두고 근거 문장을 저장한다. 판정 근거를 화면에 보여준다.
- 새로 `eligible`이 된 카페는 기본적으로 사용자 승인 대기다. 설정 "규칙 검사를 통과한 카페는 자동 승인"(기본 꺼짐)을 켜면 바로 `approved`가 된다.

### F2. 카페 글 수집 → 기존 리드 목록

- `approved`와 `eligible` 카페의 관련 게시판(구인, 알바, 외주, 자유 등)에서 최근 글 목록을 읽는다. 첫 실행은 최근 30일, 이후에는 마지막 확인 이후 글만 본다.
- 제목·본문을 읽어 기존 분석 파이프라인(`analysis/`)에 넣는다. 새 소스 ID는 `daangn_cafe`, 화면 이름은 "당근 카페". 기존 리드 목록·필터·상세·메모·영업 상태를 그대로 쓴다. 화면 리드 코드는 소스 목록이 데이터 기반이므로 고치지 않는 것을 목표로 한다.
- 이 소스는 브라우저 세션이 필요해서 `SourceAdapter`(`Fetcher` 기반 HTTP)에 바로 맞지 않는다. 브라우저 수집기가 `ParsedPost`를 만들고, 기존 파이프라인의 정규화·중복·분석·저장 함수에 넣는 방식으로 연결한다. 정확한 연결 지점은 `engine/pipeline.py`를 읽고 정한다. 공통 엔진의 `Fetcher`를 우회하는 이유와 대신 지키는 한도(F0)를 `docs/ARCHITECTURE.md`에 적는다.
- 내가 쓴 글은 리드에서 제외한다.
- 작성자 프로필·연락처·다른 글 목록은 수집하지 않는다. 본문 안의 연락처는 기존 마스킹 규칙을 따른다.
- 같은 의뢰가 당근알바와 카페에 모두 있으면 기존 유사 관계 기능으로 연결한다(자동 병합 금지).
- 새 소스의 수집 정책은 기존 관례대로 `permission_pending`으로 시작한다. 사용자가 카페 기능 확인(§2)을 하면 이 설치에서 `allowed`로 기록하고 근거는 "사용자 확인 2026-10-12"로 남긴다.
- 기본 주기: 3시간(기존 자동 수집과 같음).

### F3. 구직글 자동 게시

- 게시 템플릿(제목 + 본문)을 설정에 저장하고 화면에서 수정할 수 있다. 기본값은 §4의 글이다. 템플릿에 버전 번호를 붙인다.
- 대상: `approved` 카페의 승인된 게시판 1개. 카페당 **글 1건**만 쓴다.
- 이미 쓴 카페는 건너뛴다. 판정 순서:
  1. DB에 이 카페의 `posted` 기록이 있으면 건너뜀
  2. 카페의 "내가 쓴 글"(또는 게시판에서 내 닉네임 필터)을 확인해 같은 제목이나 본문 앞 100자가 같은 글이 있으면 `already_exists`로 기록하고 건너뜀
  3. 둘 다 없으면 게시
- 게시 후 실제 글 페이지를 다시 열어 제목·본문·줄바꿈이 템플릿과 같은지 확인하고 글 URL을 저장한다. 다르면 `posted_mismatch`로 표시하고 사용자에게 알린다(자동 수정·재게시 안 함).
- **줄바꿈 주의:** 당근 글쓰기 편집기는 붙여넣기 때 빈 줄을 지운다(사용자가 직접 확인). 클립보드 붙여넣기 대신 줄 단위로 입력하고 Enter로 문단을 만든다. 그래도 빈 문단이 사라지면 빈 줄에 한글 채움 문자 `U+3164`(`ㅤ`) 한 개를 넣는 방식으로 대체한다. 어느 방식이 통했는지 `docs/CAFE_RESEARCH.md`에 기록한다.
- 게시 한도(설정 가능): 하루 최대 5건, 게시 사이 최소 30분.
- 운영자가 글을 지웠거나 숨긴 것이 확인되면 `removed`로 표시하고 **다시 올리지 않는다.** 재게시는 사용자가 그 카페에서 직접 "다시 게시"를 누를 때만 한다.
- 설정 "자동 게시"(기본 꺼짐)가 켜져 있을 때만 예약 실행한다. 꺼져 있으면 "지금 게시" 버튼으로 승인된 카페에 한 번씩 실행한다.
- 게시 기록 상태: `pending / posted / already_exists / posted_mismatch / failed / removed / skipped_rule`. 실패 원인과 시각을 저장한다. 실패한 게시는 자동으로 다시 시도하지 않는다(중복 게시 방지). 다음 예약에서 F3 판정부터 다시 한다.

### F4. 댓글 문의함

- 게시된 내 글(`posted`, 게시 후 60일 이내)의 댓글을 30분마다 확인한다.
- 새 댓글마다 저장: 카페, 글 URL, 작성자 닉네임, 댓글 내용, 작성 시각, 답글 여부. 내 댓글은 제외한다.
- 분류(규칙 기반, 기존 선택 AI가 켜져 있으면 보조): `request`(작업 문의·견적·"가능할까요"·"연락 주세요"·"채팅 드렸어요" 등) / `question` / `other`.
- 화면에 "카페 문의" 대기열을 추가한다: 안 읽음 배지, 분류, 댓글 내용, 원문 열기 버튼, 읽음 처리, 메모, "리드로 만들기"(기존 수동 입력 경로로 리드 생성 후 연결).
- `request` 분류의 새 댓글은 Windows 알림을 보낸다(기존 알림 설정·조용한 시간 준수, 알림 문구에 댓글 원문을 넣지 않는 기존 규칙 유지).
- 답글은 앱이 쓰지 않는다. "답글 초안"은 기존 문의 초안 기능을 재사용해 화면에만 보여준다.
- 당근 웹 채팅 읽기: 구직글이 "당근 채팅으로 남겨주세요"라고 안내하므로 M0 조사에서 웹 채팅을 읽기 전용으로 볼 수 있는지 확인만 한다. 이번 범위에서는 구현하지 않고 결과만 `docs/CAFE_RESEARCH.md`에 적는다.

## 5. 데이터 (마이그레이션 `0006_daangn_cafe`)

기존 마이그레이션 관례(사전 백업 포함)를 따른다. 최소 테이블:

- `cafe` — id, url(unique), name, region, category, member_count, post_count, joined, status, status_reason, rule_evidence, first_seen_at, last_checked_at, approved_at
- `cafe_board` — id, cafe_id, name, url, kind(`job_seek` / `job_offer` / `free` / `other`), post_allowed, evidence
- `cafe_post_attempt` — id, cafe_id, board_id, template_version, status, post_url, error_code, error_message, created_at, verified_at
- `cafe_comment` — id, attempt_id, external_id 또는 (post_url + 작성 시각 + 내용 해시), author_nickname, body, written_at, classification, read_at, memo, lead_id(nullable)
- `cafe_session` — 상태, 마지막 확인 시각, 오늘 페이지 이동 수
- `cafe_consent` — 위험 안내 확인 시각, 문구 버전

백업·복원·진단 zip 규칙에 새 테이블을 포함한다. 진단 zip에는 댓글 원문·닉네임·카페 URL을 넣지 않는다(기존 개인정보 규칙). 브라우저 프로필 폴더는 백업에 넣지 않는다(쿠키 포함).

## 6. API · 화면

- `/v1/cafe/...` 엔드포인트를 기존 인증·Origin 규칙으로 추가한다: 세션 상태·로그인 창 열기, 카페 목록·상태 변경·URL 추가, 게시판 승인, 템플릿 조회·수정, 게시 실행·기록, 댓글 목록·읽음·메모·리드 만들기, 설정(자동 게시, 자동 승인, 한도, 주기).
- `scripts/gen-contracts.sh`로 OpenAPI·스키마·TS 클라이언트·fixture를 다시 만든다.
- 화면: 상단에 "카페" 작업 공간을 추가한다.
  - 상단: 로그인 상태와 버튼, 자동 게시 스위치, 오늘 사용량(페이지 이동/게시)
  - 탭 1 "카페": 상태별 목록과 판정 근거, 승인/제외/카페 열기
  - 탭 2 "게시 기록": 카페·게시판·시각·상태·글 링크

## 7. 절대 하지 않는 것

## 8. 검증과 완료 기준

자동 테스트(실제 사이트 호출 없음):

- 카페·게시판 판정 규칙, 이미 쓴 글 판정, 게시 한도·간격, 상태 전이, 댓글 분류·중복 제거 단위 테스트
- 저장한 카페 화면 HTML(개인정보는 합성 값으로 교체)로 만든 **로컬 가짜 카페 사이트**를 띄우고 Playwright로 로그인 상태 감지 → 목록 수집 → 글쓰기(빈 줄 유지 확인) → 재확인 → 댓글 읽기 → 이미 쓴 카페 건너뛰기 → CAPTCHA 화면 감지 시 정지 흐름을 확인
- 마이그레이션 0005→0006에서 기존 데이터 보존(기존 관례의 복사본 검증)
- 기존 백엔드·화면 테스트 전체 통과, TypeScript 검사 통과
- Windows 패키지 빌드(`scripts\build-windows.ps1`)와 sidecar 안에서 브라우저 실행 확인

실사이트 검증(사용자와 함께, 1회):

1. 사용자가 "브라우저 열어 로그인"으로 직접 로그인한다.
2. 카페 찾기를 실행해 후보와 판정 근거를 사용자에게 보여준다.
3. 사용자가 고른 **카페 1곳에만** 게시를 1회 실행하고, 실제 글의 줄바꿈과 링크를 확인한다.
4. 같은 카페에 다시 실행해 `already_exists`로 건너뛰는지 확인한다.
5. 사용자가 그 글에 테스트 댓글을 하나 달고, 문의함과 알림에 뜨는지 확인한다.

문서:

- `docs/CAFE_RESEARCH.md`(M0 조사), `docs/STATUS.md`(구현·검증·미검증 구분), 범위 변경 기록(§2), `docs/OPERATIONS.md`(로그인 만료·차단 시 대응, 브라우저 프로필 위치와 삭제 방법)
- 검증 자료는 `artifacts/daangn-cafe-<날짜>/`에 기존 형식(`TEST_RESULTS.md` 등)으로 남긴다.

완료 보고에는 "구현함 / 자동 테스트로 확인함 / 실사이트에서 확인함 / 확인 못 함"을 나눠 적는다. 확인하지 않은 것을 완료로 쓰지 않는다.

## 9. 작업 순서

1. **M0 조사** — 사용자가 로그인한 전용 프로필로 다음을 확인하고 `docs/CAFE_RESEARCH.md`에 URL·시각·화면 근거와 함께 적는다. 추측한 URL·선택자를 코드에 넣지 않는다.
   - 카페 검색·카테고리·지역 목록 URL, 카페 홈, 게시판 목록, 글 상세, 글쓰기 화면, 내가 쓴 글, 댓글 구조
   - 비로그인으로 볼 수 있는 범위와 로그인이 필요한 범위
   - `www.daangn.com/robots.txt`의 해당 경로 규칙(2026-10-12 확인 시 `User-agent: *`에 카페 경로 금지 규칙은 없었고 `/kr/community/s/`, `/kr/group/s/`는 금지였다. 다시 확인한다)
   - 글쓰기 편집기 종류와 줄바꿈 입력 방식
   - 웹 채팅 읽기 가능 여부(F4)
   - 화면 HTML 표본 3~5개를 개인정보 제거 후 `backend/tests/fixtures/daangn_cafe/`에 저장
2. **M1** — F0 세션 + 마이그레이션 + F1 카페 찾기·분류 + 카페 탭 화면
3. **M2** — F2 카페 글 수집을 기존 리드 파이프라인에 연결
4. **M3** — F3 게시(가짜 카페로 검증 완료 후에만 실사이트 1회)
5. **M4** — F4 댓글 문의함과 알림
6. **M5** — 패키지 빌드, 설치본 업데이트(기존 데이터 보존 확인), 문서·STATUS 갱신

각 단계가 끝날 때마다 테스트를 돌리고 커밋한다. M0 결과 당근 카페가 웹에서 글쓰기를 지원하지 않거나 로그인 세션을 유지할 수 없는 등 이 설계가 성립하지 않으면, 구현을 멈추고 사용자에게 사실과 대안을 보고한다.
