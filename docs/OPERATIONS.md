# 운영·장애·백업 안내

## 데이터 위치 (Windows)

`%LOCALAPPDATA%\Worklead\` (설치 폴더에는 쓰지 않음)

| 경로 | 내용 |
| --- | --- |
| `worklead.sqlite3` (+ `-wal`, `-shm`) | 운영 DB (WAL) |
| `worklead-demo.sqlite3` | `--demo` 실행 전용 DB (운영과 분리) |
| `logs\backend.log*` | 5MB × 5 회전. 토큰·Bearer·전화번호·이메일 마스킹 |
| `backups\` | 마이그레이션·복원 전 자동 백업, 수동 백업 |
| `exports\` | CSV·JSON·진단 zip |
| `backend.lock` | 이중 실행 방지 잠금 |

## 시작 순서와 실패

셸 → sidecar 실행 → 잠금 → 마이그레이션(기존 DB 는 먼저 온라인 백업, 실패 시 되돌림) → 워커 시작 → 서버 시작 → 준비 줄 → 화면 연결.

| 증상 | 원인·조치 |
| --- | --- |
| "로컬 서비스에 연결할 수 없습니다" | 화면의 "서비스 다시 시작". 반복되면 `logs\backend.log` 확인 |
| `already_running` | 같은 데이터 폴더를 쓰는 백엔드가 이미 있음 (다른 창·이전 프로세스). 작업 관리자에서 `worklead-backend` 종료 |
| 재시작 한도 초과 | 백엔드가 연속 3회 비정상 종료. 로그 확인 후 앱 재실행 |
| 마이그레이션 실패 | 기존 DB 는 자동 백업에서 복구됨. 로그와 `backups\*-pre-migrate-*` 확인 |

## 수집 장애

| 상황 | 동작 | 사용자 조치 |
| --- | --- | --- |
| 401/403/CAPTCHA/차단 페이지/robots 금지 | 소스 정지, 알림, 기존 리드 상태 유지 | 원인 확인. 정책상 허용·접근 정상이 확인되면 "정지 해제". 우회하지 않는다 |
| 429 | 이번 실행 부분 완료, Retry-After 까지 예약 보류 | 기다림 (필요하면 예산·주기를 낮춤) |
| 예산 소진 | 이번 실행 중단, 다음 날 이어서 | 예산 조정 (정책 범위 내) |
| 파싱 실패 증가 | 사이트 구조 변경 가능성. 정상 0건으로 기록하지 않음 | 조사 프로필 재확인 |
| 네트워크·5xx | 같은 실행에서 재시도 없음, 다음 실행에서 처리 | — |
| AI 실패·비용 상한 | `failed`/`rules_only`, 규칙 결과 유지, 자동 재요청 없음 | 필요하면 리드별 "재분석" |

스케줄은 앱이 켜져 있을 때만 동작한다. 절전·종료 중 놓친 구간은 재개 후 1회만 보충한다.

## 백업·복원

- 백업: SQLite 온라인 백업 API 로 WAL 까지 일관되게 복사하고 `PRAGMA integrity_check` 로 확인한다 (DB 파일 단순 복사가 아님). 코드: `worklead/storage.py: backup_database`.
- 복원: 워커·연결 중지 → 대상 무결성·버전 확인 → 현재 DB 백업 → 교체 → 필요 시 마이그레이션 → 실패 시 되돌림. 코드: `restore_database`.
- 현재 화면에는 백업·복원 버튼이 없다 (함수와 테스트만 존재, STATUS.md 참고).

## 보존·삭제

- 수집 원문 본문: 기본 30일 후 삭제 (설정 가능). 관심·진행 중 리드는 유지.
- 메모·영업 기록: 사용자가 지우기 전까지 유지.
- 일반 제거 시 데이터 폴더는 남는다. 완전 삭제는 `%LOCALAPPDATA%\Worklead` 폴더를 지운다 (설치 프로그램의 데이터 삭제 선택지는 미구현).

## 진단 내보내기

수집 → 내보내기 → "진단 정보": 버전, 설정(비밀값 없음), 소스 상태, 최근 실행 50건, 마스킹된 로그를 zip 으로 저장.
